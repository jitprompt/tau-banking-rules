# DEVIATIONS

Changes forced on the benchmark relative to BRIEF.md / RULES_SPEC.md / upstream tau2-bench. Upstream files untouched; code lives in `tau2-bench/jitprompt_rules/` on branch `jitprompt-rules`.

- RULES_SPEC seed dates (2026) moved to 2025: tau2's clock is fixed at 2025-11-14.
- 36 rule docs, not 32: near_duplicate rules also have two (look-alike) docs. Each near_duplicate task lists only its own product's doc in required_documents; the look-alike is the distractor.
- Golden `evaluation_criteria.actions` include writes plus only those discoverable reads a rule requires (R22-R24 ordering checks). Upstream tasks also list routine reads, which makes the DB hash depend on how often the agent calls them; omitting them keeps task pass about the writes.
- Prohibition (transfer) tasks use reward_basis [DB, ACTION] with compare_args [reason], as upstream's transfer tasks do; rule adherence itself only requires a transfer call and the absence of the forbidden write.
- For ordering rules, the control false-trigger signature is calling the prerequisite read when it isn't needed; this is benign and is reported separately from action false triggers.
- `RULES_SPEC` seeds R02/R03 changed: the existing KB already blocks closure with a pending replacement card or account age < 60 days.
- R05 dropped at Gate 2 (user decision 2026-10-15): Haiku without the rules transferred on 2/2 runs because it failed the discoverable-tool mechanics and fell back to a transfer, which is R05's required action. 23 rules / 46 tasks are run and analysed; R05's standalone doc stays in both tiers as a distractor, so the corpus is unchanged.
- `jitprompt_action` arm (improvement #1 test): tau2's grading replay runs non-strict for this arm only. The hook's output depends on what jitprompt showed earlier in the conversation, which the replay doesn't reconstruct, so strict replay aborted 7 of 92 runs as infrastructure errors (empty transcripts). Those 7 records were deleted and re-run with --auto-resume. Adherence is scored from the live transcript and is unaffected; task pass for this arm may be off where the replayed hook blocks differently.
- jitprompt 1.3.1 arms (`jitprompt_sysprompt`, `jitprompt_inband`): pinned docs are rendered by the server (per-section `# title [id: …]` / `From: … [doc …]` blocks joined by `---`, under `# Core procedures (always apply)` plus a one-line lead), not as in the harness prototype `jitprompt_pinned` (`## <doc title>` + raw content, no ids). The 1.3.1 block is ~900 characters longer. The docs were pinned by the user before this harness change; the pin step in the brief was skipped and the state recorded instead.
- From 1.3.1 on, the jitprompt client opens one MCP session per conversation for the new arms (the 1.3.0 arms shared one session per worker thread). Any future run of the plain `jitprompt` arm on RULES_XL would now receive the pinned block in-band, so it is no longer the 1.3.0 unpinned condition; the 1.3.0 baseline is the pilot batch.
- Checked on the action-hook batch: tau2's grading replay re-executes only state-mutating tool calls, not jitprompt's read tools (309 environment instances: 128 made jitprompt read calls, i.e. the live conversations and retries; 181 replayed writes only). Server-side pin-delivery counts (`tool_calls.pins`) therefore reflect live conversations only.
